# Known issues

Open issues and limitations of the workshop, with workarounds and when they can be removed.
Where the workshop comes from and what changed during its migration is in [origin.md](origin.md);
the reasons behind design choices are in [decisions.md](decisions.md).

## Platform

| # | Issue | Impact | Workaround / next step |
|---|---|---|---|
| K6 | Nexus Community Edition has usage limits (40,000 components, 100,000 requests per day) and asks for EULA acceptance. The config Job accepts the EULA. CI pipelines with `MAVEN_CLEAR_REPO` re-download dependencies from Nexus on every build. | With 30 participants the daily request count can exceed the limit; Nexus then warns and, after a grace period, restricts new components. A one-day workshop stays within the grace period. | Monitor the Nexus usage page for multi-day events; drop `MAVEN_CLEAR_REPO=true` from the pipelines to reduce requests. |
| K7 | The Dev Spaces editor definition (che-code image digests) is copied into `charts/workshop-users/values.yaml` from Dev Spaces 3.30. Dev Spaces is on the `stable` channel with Automatic approval. | After a Dev Spaces minor upgrade, pre-created workspaces keep the 3.30 editor images (still pullable) until the values are updated. | Update `devspaces.editor.*` from the `editors-definitions` ConfigMap after an upgrade. |
| K8 | Kiali is pinned (`startingCSV` + Manual approval). Newer Kiali versions are never installed automatically. | Intended (upgrade hazard of the old setup). | Change `subscriptions.kiali.startingCSV` in `charts/workshop-operators/values.yaml` together with the OSSM channel. |
| K9 | Istio gateway pods may need a restart after cluster hibernation before new Gateways route traffic. | Service Mesh module after a hibernated cluster resumes. | README, Troubleshooting. |
| K10 | Argo CD owns the `cluster-monitoring-config` ConfigMap. | On clusters that already have one, bootstrapping replaces its content. | Merge existing settings into `charts/workshop-platform/templates/monitoring.yaml`, or set `monitoring.enableUserWorkload=false` and enable user workload monitoring yourself. |
| K11 | `bootstrap.sh` gives the `openshift-gitops` application controller `cluster-admin`. | Anyone who can create Applications in `openshift-gitops` in project `default` can do anything on the cluster. | `openshift-gitops` is admin-only; participants have no access to it (verified by `isolation-check.sh`). |
| K12 | The workshop users must exist in the identity provider with the password passed as `WORKSHOP_USER_PASSWORD` (or in the credentials file, D20), and the IdP must support the password grant for `oc login -u -p` (used by the devfile's "OpenShift - Login" and the smoke tests). Running workspaces keep the password they started with until they are restarted. | On the test cluster the Keycloak realm had different per-user passwords; they were reset to `WORKSHOP_USER_PASSWORD` in Keycloak (with the owner's approval) before testing. Per-user passwords were then tested with a credentials file. | Make sure the users' passwords match before an event; with different passwords per user, use a credentials file (README "User Passwords"). |
| K13 | If Argo CD re-creates a DevWorkspace while a failed one with `spec.started: false` still exists, the new one keeps `started: false` (the field is in `ignoreDifferences` on purpose). | Seen only when deleting failed workspaces by hand. | Start the workspace from the dashboard. |
| K14 | Participants' Argo CD access uses both SSO (UI) and an API token of a local account with the same name (pipelines, devfile scripts). Tokens are issued by the `user-setup` Job and do not expire. | Tokens stay valid for the lifetime of the participant Argo CD instance. | Cleanup removes the instance; re-bootstrapping issues new tokens. |
| K17 | The `WORKSHOP_USER_PASSWORD` used on the test cluster is the old workshop's well-known default password, which the imported upstream code hard-coded. It appeared in the code repository's history (the verbatim import commit), which was replaced by a single commit on 2026-09-30; GitHub may still serve the old commits by their ID until it removes unreferenced commits. It also appears in two early commits of this repository's migration notes. No current file in any repository contains it as a credential. | Anyone who reads the public history learns that default, not a secret of this setup. | Use a different, event-specific password for real events (`WORKSHOP_USER_PASSWORD` is only stored in the cluster). |
| K18 | Fixed: in the pre-created workspaces, Terminal > New Terminal opened an empty terminal. The Dev Spaces dashboard adds `CHE_DASHBOARD_URL`, `CHE_PLUGIN_REGISTRY_URL` and `CHE_PLUGIN_REGISTRY_INTERNAL_URL` to every workspace it creates; the workshop creates its workspaces through Argo CD, so they were missing. The editor's Che API extension then passes `DASHBOARD_URL=undefined` to every terminal, and VS Code fails in the browser (`TypeError: Cannot convert undefined or null to object` in `_resolveEnvironment`) before it starts a shell. Devfile commands (Run Task) and "Create New Terminal (Select a Container)" were not affected. Found on a second cluster (OpenShift 4.21); the smoke tests had not caught it because they run commands with `oc exec`, not through the editor. | The user-setup Job now writes ConfigMap `workshop-devspaces-env` (mounted as env) with the URLs from the CheCluster status; `platform-check.sh` checks the ConfigMap and the running workspace container. | Workspaces started before the fix need a restart. |
| K19 | Kiali 2.27 (OSSM 3.4, the newest in the `stable` channel) shows Istio config read-only to participants, in Kiali and in the console's Service Mesh menu ("Editing is disabled"), although their `edit` role allows changing it (Home → Search → YAML works). Before enabling its YAML editor, Kiali runs a SelfSubjectAccessReview with the kind name as resource (`VirtualService` instead of `virtualservices`, `business/istio_config.go` `getPermissions`), which only roles with `*` match. Fixed upstream in Kiali 2.28 (`PluralResourceName`). Affects the Service Mesh lab step "Validate the result". | The users chart adds Role `kiali-edit-workaround` in `cn-project-<user>` with rules for exactly the names Kiali checks (`VirtualService`, `DestinationRule`, `Gateway`; create, patch, delete). No API resource has these names, so the rules grant nothing else; Kiali saves with the participant's own token, which `edit` covers. `platform-check.sh` checks it while Kiali is older than 2.28. Verified on a test cluster: without the Role Kiali reports update=false for the participant, with it true, and saving works in Kiali and in the console plugin. | Set `workshopUsers.kialiEditWorkaround: false` once the installed Kiali is 2.28 or later. |
| K20 | OpenShift's sample database templates "MariaDB (Ephemeral)" and "PostgreSQL (Ephemeral)" sit next to the workshop's "Coolstore MariaDB/PostgreSQL (Ephemeral)" in the Software Catalog and are easily picked by mistake. They create DeploymentConfigs (deprecated) with EOL versions: MariaDB 10.3 and PostgreSQL 10 instead of 10.5 and 15. With MariaDB 10.3 the inventory service fails at startup ("configured to run with a database version of at least '10.5.0', but the actual version is '10.3.39'"), because the guide and the solution build it with `db-version=10.5`; the catalog service works with both. Found by the owner on a test cluster; reproduced there with a temporary pod. | The platform chart hides the four sample templates (`mariadb-`/`postgresql-ephemeral`/`-persistent`): Samples operator `Config` `skippedTemplates` (server-side apply, never deleted by Argo CD) plus a Sync-hook Job that deletes them; `cleanup.sh` hands them back to the operator. The guide uses `oc rsh svc/<database>` (works for Deployments and DeploymentConfigs), the project cleanup also deletes DeploymentConfigs and TemplateInstances, and `platform-check.sh` checks the templates are hidden. | `databaseTemplates.hideSampleTemplates: false` keeps the samples (cluster shared with other users); then tell participants to pick the "Coolstore" templates. |
| K21 | Fixed: a participant's first login restarted their pre-started workspace. On the first login Dev Spaces creates Secret `user-profile` in `devspaces-<user>` (name, e-mail, user ID), labelled to be mounted into every workspace; the DevWorkspace operator adds the mount to the running workspace and replaces its pod. Measured: 38-50 s from login to ready on a healthy cluster, 3.5-4.25 min on a cluster with heavy CPU steal and slow storage, where most of the time went to setting the group of every file on the workspace volume (`fsGroup`) and copying the editor. | The user-setup Job creates `user-profile` (same name, labels and mount annotations) when it is missing, so the pre-started workspace already mounts it and the login only updates its content (verified 2026-10-01: Dev Spaces overwrote the Secret with the user's ID, labels and annotations unchanged, and the workspace pod kept running). The CheCluster sets `fsGroupChangePolicy: OnRootMismatch`, so later workspace starts skip the walk over the volume's files. | Workspaces of an existing installation pick up both changes with the next restart. |
